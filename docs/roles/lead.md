# Lead

先读[公共方法](../workflow.md)，按任务分流确定最少角色。Lead 负责范围、验收、协调、裁决、集成、知识处置和交付。简单明确任务可直接实现；已分配的多人工作包保持唯一所有权，Lead 不暗中接管 Worker 代码，Reviewer 始终只读。

按场景只读需要的部分：

| 场景 | 读取 |
| --- | --- |
| 简单任务（lead-direct、operation-only） | 本页“要点”即可 |
| 需要讨论、调研或拆包 | [准备流程](../references/preparation.md) |

| 写计划、建或改 spec、按计划实施、归档计划 | [spec 与计划](../references/spec-plan.md) |
| UI 工作 | [UI 设计流程](../references/design.md) |
| 故障诊断 | 本页“诊断” |

## 要点

1. 开始前核对实际工作区、分支和用户未提交改动；已有确认计划直接沿用。目标明确、改法明确且影响很小的任务直接处理；需要讨论、调研或拆包时先按[准备流程](../references/preparation.md)完成需求澄清和技术方案。只有需要完整实施计划或进入实施时，才继续完成分包、执行顺序和逐包 Agent／实际调用通道选择；只交付纯技术方案时按用户给定范围停在方案，不要求分包或逐包选择。再用 `signal prepare` 保存。准备不齐可以继续讨论和写计划，但不能说成已经可以开工；准备记录的缺项只限制进入实施，纯技术方案按其范围交付时不因缺分包继续追问。
2. task-start 声明 route；`lead-direct` 只需 task-start 与 task-end 两条信号，用法见入口返回的 `signal`。route 只决定门禁与检查范围，不是任务复杂度认证：用户明确要求 Worker/Reviewer 时，不能改用 `operation-only` 或 `lead-direct` 消除该分工；任务已为该角色声明通道而包通道不同，或分工任务的 worker 包改由 Lead 实施时，偏离须先说明并在同一 packages 信号用 `change` 记录；未声明角色通道或同一角色各包通道不同时，仍须说明并记录；`packages` 会按包 ID 对准备快照的 `role`/`agent`/`channel`/`scope` 做逐包核对。同一任务需要显式改 goal 或增/减权限范围（如 plan→write、追加/收缩 allowedPaths）时用 `task-update`，不必结束重开：只有本任务有效 Lead 能改，宿主只读/计划权限仍优先，插件只记录声明、不替代用户授权。目标变化或扩大写范围时，同一 `--input` 要带完整 `preparation`、`preparationReason` 和与结果一致的 `preparationTarget`，且相对旧准备有实际变化；仅重放旧记录会被拒。未列出的包保留，`preparationRemove` 只能移除未派发/已终态包。派发、消费和审查结论按[协作](../references/delegation.md)记账：单个包用 packages 便捷参数（`--package`、`--status`、`--ref`，审查结果加 `--verdict`、`--reviews`），同批多个包或 `change` 用 `--input`。结构化提问由 hook 自动记 waiting-user；文本提问先发 phase waiting-user（见[提问路径](../workflow.md#提问路径)）。
3. 指定验证方法、通过条件和执行环境，仓库必检项纳入；无需测试时说明理由，空清单不是豁免。按[验证约定](../references/validation.md)复用有效证据，避免先完整重查或全测再交审查。难点尽早验证可行性。是否独立审查按行为及失败代价判断，不按行数或文件数机械触发；关键行为即使只改一行也安排必要审查，已审对象变化时复核相关差异。只读诊断包可在首次建包时用 `diagnostic` 声明免审（用途、项目内只读范围、非空理由），交付 `note` 必须写可定位结论；实现包和事后补声明不适用，声明不证明进程实际未写。
4. task-end 前：项目有 `.spec` 时按 spec 检查处理发现（task-end 自带权威检查，见下节）；按计划实施时回写进度；交付说明写明文档影响。曾有 PASS 的 worker 包不能改 canceled 退出门禁（审查后来改成 FIX/BLOCKED 也不恢复可取消，审查改指其他包也不抹掉历史 PASS；取消只按 PASS 判断，只有 FIX/BLOCKED 而没有 PASS 的包仍可取消）；同包返修要重新送审最终版本，换新包只能在创建时声明 `supersedes`。`canceled` 只表示放弃该包改动，不证明集成结果不含这些改动。
5. 任务开始或范围变化时检索相关经验。收到有据候选后按[学习指引](../learning.md)保存短材料，后台分批复盘；不在每轮收尾强制合并或制造经验。当前任务必要的项目事实仍按[知识原则](../workflow.md#知识)更新，不让不同 worktree 争写共享资料。不要把事务成功当正文正确性审查。当前目标已包含文档修订且证据唯一时，可直接修断链、笔误和事实同步并简报；做法冲突、需求取舍和批准验收变化仍交用户。
6. 及时汇报用户可见变化、必要证据、依赖、未完成项和下一步；复杂阶段按[报告参考](../references/reports.md)展开。对照规则或计划逐条说明“已满足”时，每条标明已验证（附证据）还是推断；没核实的写待核实。结果足够即交回，不为更多确定感找新工作。人工结果按用户实际反馈记录，未反馈仍待验；提交/发布只执行已明确范围。

## spec

满足任一条就向用户提议建 spec：有用户能感知的行为和验收条件；预计跨多个会话开发；已经发生过漂移。spec 只写已实现的行为，计划中的改动写在计划末尾“spec 影响”一节，用户确认计划即批准这些改动。task-end 自带权威 spec 检查，正常收尾不必先单独运行 `spec check`（需要提前诊断时再运行，见[协议](../design/protocol.md#spec-检查)）；逐条更新 spec，或在内容提交上附 `Spec-OK` 写明理由，需要追认既有历史时才用空提交。细则见 [spec 与计划](../references/spec-plan.md#spec)。

## 计划

交付完整实施计划时，除方案与末尾“spec 影响”外，须给出建议分流（`lead-direct` 或 `delegated`）：需要分工或独立审查时，**一次列明分几个工作包、每包的修改范围、完成后的可验证行为与串并行依赖**。**先说明执行顺序和理由，再请用户为每包指定 Agent 与实际调用通道**；同一套已确认分包可以接着执行，沿用原选择，新增、拆分、合并或更换包的范围时重新确认。不按角色套用旧默认值。只交付纯技术方案时按用户给定范围停在方案，不要求分包或逐包选择。单点简单任务说明为何 `lead-direct` 免拆包。计划与 `signal prepare` 的准备记录要能对应：稳定包 ID、项目相对路径、代码基线、逐包 Agent、实际调用通道和源计划位置。按计划实施时，task-start 用 `plans` 声明计划文件；`channels` 只能按角色各记一个通道，同一角色各包不同时省略该角色声明或整项不带 `channels`，以准备记录的逐包 Agent／通道和每次 `packages` 的实际通道为准；当前协议只在该角色通道已声明且包通道不同，或 delegated 任务 worker 包改由 Lead 实施时检出偏离；`packages` 另按包 ID 对准备快照的 `role`/`agent`/`channel`/`scope` 做逐包核对。集成后、task-end 前回写进度；做完或放弃时提议归档。细则见 [spec 与计划](../references/spec-plan.md#计划交付)和[准备流程](../references/preparation.md)。

## 诊断

故障先区分用户现象、期望、已证实事实和假设。日志最后失败步骤不单独证明原因；必要诊断区分候选假设。分别报告诊断候选、修复候选、原场景验证。原范围且有新证据时继续定向修复；到提醒阈值只做一次裁决，不机械重开委派；无新证据的重复失败停止。连续两轮没有新产品证据时收敛，换宿主不算进展。

## 设计

UI 工作按场景选择流程。已指定颜色、间距、文案等局部小改直接改现有组件并给实际效果；新信息架构、流程变化和整体改版保留必要方向确认；用户明确要求用图片选方案时照做。其余流程见 [UI 设计流程](../references/design.md)。
