# spec 与计划

Lead 写计划、建或改 spec、按计划实施、归档计划时读本页。命令与门禁细节见[协议](../design/protocol.md#spec-检查)。

## 计划交付

需要讨论、调研或拆包的任务，先按[准备流程](preparation.md)完成需求澄清和技术方案；只有需要完整实施计划或进入实施时，才继续完成实施安排。只交付纯技术方案时，按用户给定范围停在方案，不列分包、逐包 Agent 或通道。写完计划向用户交付时，不光给技术方案，还要把执行分工一次对齐，避免用户说“开始实施”后再停下来反问一轮：

1. **分流与分包**：明确建议 `lead-direct` 还是 `delegated`。若为 `lead-direct`，用一句话说明为何无需拆包、是否需要独立 Reviewer；若需要分工或独立审查，直接列出分了几个工作包，每包写清 `packageId`、角色（Worker / Reviewer）、负责范围（文件或模块）、完成后的可验证行为和串并行依赖，不为凑人数强拆耦合代码。
2. **先顺序、后选人**：先说明执行顺序、哪些包可以并行、哪些必须串行及理由，再请用户为每个包指定 Agent 与实际调用通道。已确认的同一套分包可以接着执行或原位返修，沿用原选择；新增、拆分、合并或更换包的范围时，展示变化后的包并重新请用户指定相关包。不要按角色套用旧默认值，也不要求用户为了换会话或换电脑重新选择。当前 `task-start --channels` 只能按角色各声明一个通道（`{worker?, reviewer?}`）：同一角色不同包使用不同 Agent 时，不要给该角色填一个会与实际包冲突的默认值，可省略该角色键，必要时整项不带 `channels`，以准备记录里的逐包 `agent`/`channel` 和每次 `packages` 的实际通道为准。当前协议只在任务已声明该角色通道而包通道不同，或 delegated 任务 worker 包改由 Lead 实施时检出偏离并要求 `change`；未声明角色通道或同角色逐包不同时没有可比声明，仍须向用户说明并记录，逐包核对留 W2。
3. **保存准备**：计划正文保留需求、调研、方案、工作包、逐包 Agent、实际调用通道、确认范围和验收对应关系，并用 `signal prepare` 保存结构化记录和源计划摘要。稳定包 ID、项目相对路径和代码基线要能从 Markdown 直接读出；本机会话 ID、票据和绝对路径不作为跨电脑的批准依据。
4. **spec 影响**：计划末尾保留“spec 影响”一节（无影响写“无”），与分包、角色通道在同一次计划确认里拍板。

准备记录不齐时，回执列出具体字段（如“工作包 W2 尚未指定 Agent”“工作包 W2 尚未填写实际调用通道”），不要泛泛说“计划不完整”；可以继续讨论和写计划，但不能宣称准备完成或已经开工。准备记录是 Lead 整理的可核对声明，不是对用户批准真实性的自动证明。

## spec

满足任一条就向用户提议给功能建 spec：有用户能感知的行为和验收条件；预计跨多个会话开发；已经发生过漂移。用户确认后写入 `.spec/<id>/spec.md`（frontmatter 的 `code:` 只列具体文件，正文写目标、原因、验收、边界；目录名即 id，`.spec` 内不得重名）。小修改、一次性脚本不建。长期设计说明放 `.spec/design/spec.md`，架构说明可选放 `.spec/architecture/spec.md`。

spec 只写已经实现的行为；计划中的改动留在计划文档里，不提前写进 spec。写计划时在末尾加一节“spec 影响”：列出要新建、修改、删除的 spec 及条目，写出改后的验收句子；不涉及 spec 时写“无”。用户确认计划（说“执行”）即同时批准这些 spec 改动，不再单独确认。计划原本没有这一节、由 Lead 事后补写时，补写内容不算已批准：派工前把补写的“spec 影响”交用户确认。实施时 Lead 按这一节把改后验收句子写进 Worker 和 Reviewer 的包作为验收（实施期间以包内验收为准，旧 spec 正文仍描述现状），集成时改 spec，与代码在同一任务内提交。计划没写到的 spec 改动，或要改已批准的验收，才再问用户。计划全部实施后归档，不转成 spec。

task-end 自带权威 spec 检查，正常收尾不必先单独运行 `spec check`；需要提前定位时再运行。逐条更新 spec，或在内容提交上附 `Spec-OK` 写明理由；需要追认既有历史时才按现有空提交语义放行。纯重构可由 Lead 放行，改 spec 的目标、原因、验收、边界正文先经用户同意（已确认计划的“spec 影响”所列改动算已同意），只同步 `code:` 路径可直接处理。

## 计划回写

任务按计划实施时，集成后、task-end 前在原计划里回写进度：本任务完成了哪些条目、与计划的偏离及原因、还剩什么。只写状态和指向提交或证据的链接，不搬过程记录；计划里的已知问题、反例表等随实际结果更新，不留过期结论。回写的计划路径列入任务 allowedPaths。task-start 时用 `plans` 声明本任务对应的计划文件（见[使用说明](../usage.md#任务与回执)）：收尾时计划仍未改动，Stop 和 task-end 回执会提醒回写，不阻止结束；确实不需要回写时在交付说明里写明理由。

## 归档

计划条目全部完成或经用户明确放弃时，Lead 提议归档，用户确认后按以下步骤做：

1. 移到项目的归档目录（项目已有约定按约定，没有时用 `docs/archive/`），用 `git mv` 保留历史；
2. 开头加一行状态：已归档、完成日期、对应版本或提交；放弃的条目注明原因；
3. 仍未完成的条目抽成短待办或并入下一份计划，不让它们只留在归档文件里；
4. 修好全部引用：`AGENTS.md` 导航、对齐索引、其他文档的相对链接，以及代码、测试、fixture 里写到的路径；
5. 以上涉及的路径都列入 allowedPaths，范围不够先补授权，不越界改动。

归档后对齐索引按增量更新。计划格式各项目不同，插件不对计划设硬门禁，也不判断计划是否做完：只提醒“声明了的计划没回写”，是否做完由 Lead 对照条目判断并在交付说明里写明。
