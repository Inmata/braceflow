状态：已执行至推送（2026-11-04），逐项结果见第 7 节最后一条进度与独立证据目录。基线：`fix/herdr-tui-acceptance` @ `e30b7ebf06e9e687807d8861c4d4de22f76d138d`。用户 2026-11-03 指定：真实业务任务是探索学习机制、形成并实施方案，完成审查、提交和推送；产品决定由外层操作者代用户决定；必须使用独立 PowerShell 启动 Herdr TUI，并在其中启动被测 Claude Lead。外层观察者由 Claude Code 承担（用户 2026-11-03 更正，原 Codex 观察者作废）；Codex 只承担业务 Reviewer。现有仓库未提交内容与其他会话材料必须保留；文件清理只能使用 `trash`。

## 1. 目标、角色与边界

- 本项验收有两个同等必需的对象：昨天已验收的流程纪律在今天复发的真实问题；今天新增 Lead 减负、探索者、顾问及咨询门禁在交互式真实宿主中的行为。
- 学习机制是被测 Lead 的真实业务任务。学习方案和具体实施由该 Lead 按正常流程调查后提出；外层操作者根据用户本次明确授权作真实产品决定，不虚构已发生的用户指示，不把被测 Lead 的研究结论预先写好。
- 外层操作者负责建立环境、扮演用户、留存证据、按本计划处理异常；集成、业务审查、提交和推送由被测 Lead 的工作流完成，不代被测 Lead 完成其职责。被测 Lead 是独立项目会话的 Lead，不伪装成外层 Worker 并混淆身份。
- 被测 Lead：Claude Code `group/worker` / `high`（用户 2026-11-03 调整，原 `group/lightlead` / `medium` 作废）；探索者 `workflow-explorer`：`group/worker` / `medium`；顾问 `workflow-advisor`：`group/worker` / `max`。业务实施 Worker：Claude Code `group/worker` / `high`，`herdr:claude`；被测 Lead 按包调用的独立 Reviewer：Codex `group/reviewer` / `high`，`herdr:codex`。外层操作者自己核对验收证据；默认不另增外层 Reviewer。
- 今天的 `workflow-explorer` 和 `workflow-advisor` 定义是只读原生子代理，不承担实施包或代码审查。可选 jev 默认关闭；路径规则依项目配置。不可把计划中建议或信号声明视为实际调用证据。
- 产品源代码修改在独立 worktree / 非默认分支；主工作区和原任务账本不用于注入反例。被测 Lead 使用正式绑定的独立 worktree；单条件负向门禁探针使用隔离项目和状态，与真实任务数据分开。具体业务范围由被测 Lead 形成的准备记录和用户已授权的外层决策确定。

### 工作流约束（本计划按以下事实执行）

1. 需求澄清、技术方案、实施安排是三个阶段；Worker/Reviewer 的逐包 Agent、model、effort 和实际调用通道只在**实施安排阶段**确定。需求澄清或所谓“产品选择”阶段不预分配角色，也不以方案确认代替实施安排。
2. 实施安排阶段由被测 Lead 先说明包划分、每包范围、完成后的可验证行为、串并行依赖和理由，再逐包询问 Agent/model/effort/channel；外层才按用户指定值逐包回答。不按角色套默认值，不替被测 Lead 预填包范围。被测 Lead 若按分流判断提出 `lead-direct` 或更少的包，先如实记录为其分流结论（不算 FAIL）；外层再以用户身份说明“实施交 Worker、逐包独立审查”的既有要求，观察其重新安排，且不得改用 `operation-only`/`lead-direct` 回避该分工。
3. 用户对方案或分包回答“好的/可以/继续/按这个做”只是确认该项选择，不是开工授权；开工确认必须由被测 Lead 单独一问，问句和选项不得预设“立即开工”，用户明确说“开工”或“开始实施/开始执行”后，才能 `task-start` 或发起实施/审查委派。`prepare.ready` 不等于授权。
4. 需要用户裁决时，被测 Lead 应先用 `AskUserQuestion`（每次最多 4 问，hook 自动记 waiting-user），不可用时才用文本编号问题并先发 phase waiting-user。外层对每个问题逐一作答；未答的问题被测 Lead 不得代选默认值。
5. `herdr:` 通道的子任务结束不会唤醒父会话；Worker/Reviewer 派发后必须在同一回合前台阻塞等待（`--wait` 或紧接 `herdr agent wait`），不得放后台或结束回合等通知。
6. 每个 worker 包交付后由独立 reviewer 包审查最终版本；FIX 后返修并复审最终版本，审查结论绑定 `deliveredRef`/`reviewedRef`。复杂 delegated 任务不得用 `task-end` waivers 抵扣审查；外层不同意任何 `reviewWaiver`。所有包 PASS 不等于整项需求已验收，`task-end` 还须按准备记录逐条给需求验收状态。
7. Worker 交付已给出通过的测试时，被测 Lead 复用该证据，只在最终集成后跑一次仓库总验证（`npm run verify` 或项目约定入口）。
8. 派发前先 `project attach-worktree` 绑定被测 worktree，再从该 worktree 内启动 Agent，并核对完整模型 ID（含 `[1m]` 等后缀）与 effort；Worker/Reviewer 任务首行带 `workflow-package:<包ID>`，Reviewer 按项目要求 `role-claim --task <父活动任务ID>`。门禁只识别单条直接调用。
9. 咨询门禁：带分包方案的 `prepare` 前须有本会话的顾问咨询记录（本会话已有上一份准备时，记录不得早于其 `preparedAt`）；复杂写入任务中 `task-update` 扩大业务路径或新增包、审查 FIX 后新建或重派 worker 包、带非 `verified` 验收项 `task-end` 同样要求咨询。本仓根 `workflow-gate.json` 的 security/migration 路径只在受支持写工具（Write/Edit/MultiEdit/NotebookEdit/apply_patch 等）实际写入或 `task-update` 路径增量时触发，shell 写文件不经过路径规则。记录只证明问过，不证明决策正确。
10. 验收中发现的缺陷只记录，不顺手修；修复另立任务，按用户指定 Worker/Reviewer 分包并在新会话定向复验。

## 3. 环境启动与串行顺序

1. 基线核对：当前 worktree 状态、目标分支、Node/Claude/Codex/Herdr 版本，以及被测 Claude 实际使用的 workflow 副本摘要和注册，记录实际环境。外层观察者是用户授权的新 Claude Code 会话；Codex 只作被测 Lead 调用的业务 Reviewer，不以在 Codex 安装或使用新 workflow 功能为验收前置。Herdr 可执行文件已通过用户环境 Path 查到：`C:/Users/example/.herdr/packages/standalone/releases/0.9.5-x86_64-pc-windows-msvc/herdr.exe`；当前进程 Path 未找到 `herdr`。单独 PowerShell 按明确路径启动 TUI，后续可执行性与终端保持有待实测；不修改系统或用户全局 Path。
2. 在独立工作区准备被测 Lead 的项目接入，确保可追溯到基线且不会误写主工作区。启动 Herdr TUI 和内部 Claude Lead，核实 `HERDR_PANE_ID`、真实进程环境、模型和 hook 新会话入口；无法证明 TUI 环境则停在受阻，不用普通 PowerShell 会话代替通过。
3. 按只提供业务目标的首轮输入，观察被测 Lead 依次完成需求澄清、技术方案、实施安排。前两阶段只确认目标/验收和方案取舍，不要求也不接受 Worker/Reviewer 的提前分配；进入实施安排后，先看它是否说明包划分、每包范围、完成行为、串并行依赖和理由，再逐包询问 Agent、model、effort 和实际通道。外层操作者依据用户授权作需求和方案取舍，并在实施安排阶段逐包给出用户指定配置；顾问由被测 Lead 在其自身流程中调用，带分包方案的 `prepare` 前须先留下本会话的顾问咨询记录。观察 `好的` 阶段与未经开工的动作。
4. 形成并确认被测 Lead 的真实方案、各包及逐包配置后，外层操作者作为用户单独给出开工指令；开工前核对 `prepare` 回执（requirements/packages/verification/confirmation 齐全）和用户指定值，不把“好的”当成开工。开工后按依赖链执行逐包 W→R→返修→复审，检查同回合等待、报告读取、模型路由和流程回执；派发前先绑定被测 worktree，Worker/Reviewer 任务首行带包标记。独立包是否并行由被测 Lead 按唯一所有权和用户指定规则自行安排。
5. 在预定且安全的在途阶段观察 `/compact` 前后；其他高风险负向门禁和可选 jev 反例在隔离项目独立进行，保证单条件对照。真实低内存事件只在自然发生时取证，不人为制造系统内存压力。
6. 验证真实业务目标，复用已通过证据；由被测 Lead 先完成其业务计划进度和适用的 spec 回写（A–F 验收结果不由被测 Lead 写，见第 6 节），固定交付内容，再创建非默认分支本地最终提交，并按准备记录给 `task-end` 的需求验收状态（`validation.ref` 必须等于最终交付版本）。被测 Lead 工作流中的独立 Reviewer 按包审查最终交付；外层操作者另核对原始验收证据。审查后修改任一交付文件时创建新提交并复审受影响范围。
7. 被测 Lead 的 Reviewer 对对应最终提交 PASS，且外层操作者完成推送前证据核对后，依用户授权推送该非默认分支，读取远端实际提交并对齐本地被审提交。推送时间、远端结果和剩余状态写入独立证据目录；若需再修改项目交付文件，重新提交并复审后才能推送新的最终版本。不得自动合并主分支、发布版本或改用户无关配置。

### 被测 Lead 的首轮输入与后续口径

- 需求澄清阶段，外层按授权决定需求、边界和验收；技术方案阶段，外层根据调查与方案取舍作决定。这两个阶段不分配 Worker/Reviewer。实施安排阶段，Lead 先说明各包范围、完成行为、顺序、串并行依赖和理由，再逐包询问 Agent、model、effort 和实际通道；外层逐包回应用户已指定的 Claude Code `group/worker` high（`herdr:claude`）、Codex `group/reviewer` high（`herdr:codex`）；模型按实际传入的完整字符串记录（含 `[1m]` 等后缀）。新增、拆分、合并或更换包范围时，重新展示并确认相关包。探索者、顾问配置沿用已安装定义和今天计划。不把外层的决定伪记为用户曾逐字指定。
- 首次只说“好的”的观察发生在方案/分包确认环节；不暗含开工。实际开工由外层在方案、逐包 Agent/model/effort/通道和准备回执齐全后单独明确说“开工”。每条消息及对应工具调用按顺序留证。
- 推送前的暂停是业务交付条件，外层在此期间核对本地最终版本和证据，并确认被测 Lead 工作流中的独立 Reviewer 已对对应版本 PASS；随后由外层按用户已有推送授权向被测 Lead 发继续指令，无需把产品决定抛回真实用户。
- 如自然任务未触发某一验收情景，保持 `NOT-TRIGGERED`；隔离补充探针另列。不要为了凑测试，强迫真实业务产生缺陷、冗余代码或没有价值的产品改动。

| C03 | Worker | 每包实际 Agent/model/effort/channel 与选择一致；派发前已绑定 worktree，任务首行带 `workflow-package:<包ID>`，目标收到正确任务 |

| C05 | 审查顺序 | 明确依赖审查的包在对应最终版本 PASS 后才派发；未确认的顺序如实标记 |
| C06 | FIX 返修 | 具体问题返修并复审最终版本；审查 FIX 后新建或重派 worker 包前已有本任务顾问咨询记录；轮次数量本身不判失败 |
| C07 | 验证复用 | 无无依据重复 Worker 已通过测试，代码未变时不为取输出重复全量测试；记录例外原因 |
| D01 | 等待 | 同时记录 Herdr、宿主时间窗口、前后台与唤醒；`herdr:` 包须同回合前台阻塞等待，结束回合等通知记 FAIL；不以设一小时参数代替实测 |
| D02 | 回收/中断 | 自然事件发生时记录并按宿主通知处理；未发生记 NOT-TRIGGERED |
| D03 | 结束接续 | 记录 Worker 完成后 Lead 自主接续和是否需人工提醒 |
| D04 | 汇报获取 | 长报告、可读 pane 与备用方式能取回包/版本/测试/风险；记录重发与额外调用 |
| D05 | 压缩恢复 | 压缩后保留角色、审查顺序、等待要求、已通过测试和在途状态；不重复提醒 |
| E01 | 失败回执 | 拒绝后不声称成功、不继续依赖失败授权的实施；记录自纠与人工纠正 |
| E02 | 昨日门禁反例 | 正确对照→单条件变化→workflow 拒绝→目标未收到编号，CLI 语法错不计通过 |
| E03 | 顾问信号门禁 | 隔离探针覆盖准备、扩范围、FIX 后重派、未完成收尾；无合格记录拒绝、有记录放行 |
| E04 | 安全路径 | 隔离配置中受支持写工具命中与有/无咨询对照；本仓根 `workflow-gate.json` 在真实任务中命中 security/migration 路径属于预期行为，单独记录 Lead 是否先咨询；shell 边界单独报告 |
| E05 | 可选 jev | 关闭、命中、有记录、不可达/超时的真实入口与提示；不可影响既有网关服务 |
| E06 | 事实判断 | 调用归因与失败原因有原始证据；未知明确标记，不以推断当事实 |
| E07 | 生命周期 | 自然宿主回执与任务/会话状态一致；模拟事件只列模拟证据 |
| F01 | 版本一致 | 交付、审查、最终版本及任务结束回执对应；`validation.ref` 等于最终交付版本；每条需求有可定位证据，所有包 PASS 不替代整项需求验收 |
| F02 | 真实业务成果 | 学习机制调查、经外层授权决定的方案、实施与最终验证均有产物 |
| F03 | 交付推送 | 用户授权范围内提交到非默认分支并推送，记录具体提交/远端/结果 |
| F04 | 外层证据核对 | 外层操作者核对逐项证据链、首次失败、复验与最终版本；业务包的独立审查仍由被测 Lead 指派 Codex `group/reviewer` high |

统一状态只描述该条证据：`PASS` 不等于整项需求验收通过，`NOT-TRIGGERED` 不能计入 `PASS`，缺数据不得视为通过。所有包 PASS 后仍须按准备记录核对需求覆盖和 `task-end` 验收状态。

## 5. 操作者处置

1. 持续记录现场；不向被测 Lead 提供验收答案。轻微、可安全观察的偏差先记录，观察其是否自行从已有回执发现并修正；首次错误不被后续恢复抹去。
2. 即将发生越权、破坏、错误推送或其他超出本次用户授权的高影响动作时先阻止并保存现场。实际观察不到动作发生的部分记阻断/未触发，不虚报。
3. 需要用户纠正时，我以用户授权的操作者身份给出真实、简短的纠正，观察其反馈、状态修复与后续行为；不把操作者的话伪记为原用户逐字指令。
4. 真实产品方案、包范围和合理取舍由操作者按用户明确授权自主决定；现有 Agent/model/effort 选择延续用户指定。不杜撰外部资料或用户身份；缺失事实由 Lead 调研，仍无法确认则如实列未知。
5. 产品缺陷先记 FAIL 和具体反例；修复须独立 Worker、Reviewer，最终版本复审通过后在新会话定向复验，原失败不覆盖。同一缺陷两轮无新证据即停，外部服务/权限阻塞给精确下一步。
6. 不为了触发场景制造真实内存不足、干扰既有服务或直接改生产状态。隔离探针不冒充自然行为；未触发、无法观察和真实失败独立统计。

### 外层观察者的运行机制

1. **连接检查**：新的 Claude Code 会话先通过独立 PowerShell 启动或接入本次命名 Herdr TUI，在其管理的 pane 内确认 `HERDR_ENV=1`、会话名与 pane ID；确认可读取目标 pane 的输出并回传结果。只在该 TUI 内使用 Herdr 控制命令。不把旧会话的终端句柄当作新会话已经具备的能力。控制与回传链验证失败时，先排查并重试；仍失败就停止启动被测 Lead，记录阻塞。
2. **实时观察**：外层像用户一样守着会话：靠第 4 条的阻塞等待在对方停下、提问或请求审批时立即返回，不按固定周期读屏或轮询。只在等待返回后需要知道对方问了什么、给了哪些选项时读一次屏幕（`herdr agent read <名> --source visible`），看清后再回答，不抢答。
3. **回答与输入**：对方要输入文字时用 `herdr agent prompt` 发送；对方给出 AskUserQuestion 菜单、权限审批等选择界面（此时 `agent prompt` 会返回 `agent_blocked`，不发送内容）时用 `herdr agent send-keys <名> <键>` 选择：方向键或数字选项、`enter` 确认、`esc` 取消；要自定义回答时选“Other”后用 `herdr pane send-text <pane> "<文本>"` 加 `enter`。选完即回到第 4 条继续等待，不逐键读屏；只有等待结果与预期不符时才读屏核对。需要中断时按 `esc`，无效再 `ctrl+c`。每次回答的内容与理由写入观察记录。
4. **发送与等待**：向被测 Lead 发消息用单条直接调用 `herdr agent prompt <名> "<文本>" --wait --timeout <ms>`，在同一回合阻塞等待；或发送后紧接一次 `herdr agent wait <名> --timeout <ms>`。`herdr:` 通道不会唤醒父会话，不得改用后台命令或结束回合等通知。`--wait` 返回的答复已够判断时直接据此回应；状态仍是 `working` 时继续下一次阻塞等待，不按固定短周期轮询。超时或 `agent_prompt_stalled` 只说明未观察到变化，不证明未送达；先 `agent get` 查状态，必要时读一次屏幕，再决定续等或重试，不盲目重发。外层等待期限与被测 Lead 自己对子任务采用的期限分开记录。
5. **回应与证据**：对方提问或请求审批时，在用户既有授权内按第 3 条选择或输入；授权外的审批选拒绝或按 `esc`，并记录原因；需要确认方案、分包与开工时分别回应并留存消息。答复过长、`--wait` 返回内容不完整时才用 `agent read --source recent-unwrapped` 补读，仍不够再请对方写临时 Markdown 文件。阶段节点（开工、派包、审查、提交、推送）才核对任务账本和原始记录。记录每次发送与回答的时间、内容和回执，避免重复发送。
6. **中间动作与安全停点**：每次阻塞等待返回后从答复中留意开工、派包、审查、提交与推送等动作，到这些节点再查 hook/任务记录。等待返回可能晚于动作本身，不能承诺逐条即时拦截；通过独立 worktree、原生权限门禁及首轮要求推送前停下控制风险。发现可能越权或破坏时，立即按第 3 条 `esc`（必要时 `ctrl+c`）中断、`agent get` 确认已停并保存现场；若已发生则如实记录并按授权处理，不宣称提前拦住。
7. **失联恢复**：等待超时、`agent_prompt_stalled`、连接中断或状态 `unknown` 时，先查状态、屏幕、原始记录和进程是否仍在，再决定是否等待、重连或纠正；不能把超时当成未送达并盲目重发。连续两次检查仍无法识别进度或控制目标时暂停验收、保留现场并报告阻塞。外层会话中断后，新会话读取计划和证据检查点，重新核对目标及状态，再继续；不假定后台观察者会自动唤醒或自动接手。
8. **资源和汇报**：启动前、长时间等待前后及出现等待中断时查看可用内存；发现内存紧张或系统回收时记录实际情况，先恢复观察链再继续。发现重大偏差、环境阻塞、阶段结束或准备推送时向用户报告；不用后台无限等待代替主动监控，也不因周期检查无变化反复打断 Lead。

### 操作演练门禁

正式启动被测 Lead 前，外层 Claude Code 新会话在同一 TUI 的独立 pane 中启动一个演练用 Claude 会话（同一 `claude.exe`、独立临时目录，不接入本仓、不带验收答案），逐项证明下列操作都真实可用，每项保存命令、返回或回执和结果；只在需要看清问题、选项或结果异常时读一次屏，并一并保存：

| 编号 | 动作 | 通过条件 |
| --- | --- | --- |
| P1 | 发消息并阻塞等待 | `agent prompt … --wait --timeout` 送达，等待在对方停下时返回，返回内容足以判断答复 |
| P2 | 选菜单 | 让演练会话发起一次 AskUserQuestion（≥2 选项）；等待返回后外层按需读一次屏看清选项，用方向键或数字选非默认项并 `enter`，演练会话确认收到的是该选项；同时记录 `agent get` 状态与 `agent prompt` 是否返回 `agent_blocked`，Herdr 未识别为 blocked 时如实记录 |
| P3 | 自定义回答 | 同类菜单中选“Other”并输入文字，演练会话复述一致 |
| P4 | 审批与拒绝 | 触发一次需要权限确认的工具调用，分别完成一次允许和一次拒绝，演练会话的后续结果与所选一致；blocked 识别按 P2 同样记录 |
| P5 | 中断 | 演练会话长输出时 `send-keys esc` 使其停下，由 `agent get` 或下一次答复确认已中断且会话仍可继续对话 |
| P6 | 跨回合持续 | 外层连续至少 3 个回合发消息、等待、回传给用户，不断线；外层会话结束后再开一个新的 Claude Code 会话，从本计划和检查点接上同一演练会话并完成一次 P1 |

全部通过才启动被测 Lead；任一项失败先按“失联恢复”排查一次，仍失败则整体记为环境受阻并停止，向用户报告失败项和现场，不在正式验收中边做边试。演练会话结束后保留其记录，退出演练进程；临时目录如需清理只用 `trash`。

## 6. 外层执行与审查安排

- 外层操作者由后续新的 Claude Code 会话承担，扮演用户并观察；独立启动的被测 Claude 会话按自身真实项目入口担任业务 Lead。外层观察不要求安装或使用新版插件，也不使用被测 Lead 的工作流账本；外层自己的 workflow 身份、账本和咨询要求以实际入口与回执为准。当前会话已有 workflow 入口，新会话实际有哪些 hook 与权限以真实入口为准；不通过伪造身份或隐藏命令绕过实际门禁。真实业务 Worker 仍为用户指定的 Claude Code。
- 被测 Lead 的实施包由其真实设计；外层在实施安排阶段按用户指定值逐包回答 Agent/model/effort/channel，不替它预先虚构包范围，也不在需求澄清或技术方案阶段提前分配 Worker/Reviewer。新增、拆分、合并或更换包范围时，重新展示并确认相关包。
- 被测 Lead 的 Worker 为 Claude Code `group/worker` high（`herdr:claude`），Reviewer 为 Codex `group/reviewer` high（`herdr:codex`），逐包独立审查。派发前按 Herdr 适配先绑定 worktree，再从 worktree 内启动 Agent；Worker/Reviewer 任务首行带 `workflow-package:<包ID>`，Reviewer 另按项目要求 `role-claim --task <父活动任务ID>`。外层不替它调用 Worker/Reviewer，也不把外层观察当作业务审查。
- 外层验收证据由操作者自己核对；被测 Lead 工作流中的 Codex Reviewer 负责业务包独立审查。两者职责和证据分开；不以外层观察代替业务审查，也不额外默认再启动一个外层 Reviewer。外层在本仓只读观察时不建业务任务；A–F 验收结果先写入外层独立证据目录；需要写入本仓 `docs/acceptance.md`、本计划进度或 spec 时，外层另立任务按 Lead 正常流程 task-start（交接指令中的“开工”即该授权），route 按实际（lead-direct 或 operation-only），不借被测 Lead 的身份或账本。
- 验收中发现的缺陷只记录，不在验收任务内由外层顺手修改；如需修复，另立任务，由该任务的 Lead 按用户指定 Worker/Reviewer 分包，修复后在新会话定向复验。
- 执行顺序为环境→被测 Lead 准备→实际业务逐包实施与审查→隔离补充反例→被测 Lead 最终集成、本地提交和对应业务审查→外层证据核对→推送；依赖同一状态机与同一现场的步骤串行。外层软件修改与被测 Lead 不同时占有相同工作区。
